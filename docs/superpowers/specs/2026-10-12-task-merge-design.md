# 卡片 worktree、主分支合并与实际状态

日期：2026-10-12。状态：书面设计及实施计划已获用户确认，代码已实现并通过限定测试；实际证据、独立审查修复及运行状态见 [验证记录](../../development/web-task-merge-verification.md)。本文件不授权开发者提交、合并或推送开悟当前仓库。

## 用户已确认的目标

- 每张卡片在独立 Git worktree 开发，继续使用原卡片的独立 pi 会话。
- 项目默认使用主分支，不要求添加项目时手动选择；特殊项目可以额外设置。
- 卡片开发后提供合并主分支的按钮，也可通过任务聊天发起。
- 不论按钮、AI 执行 Git 命令还是用户在外部 Git 操作，卡片均根据实际 Git 状态显示合并情况。
- 保留左侧专题看板、右侧聊天和轻量界面。专题、执行状态、合并状态相互独立。

## 已确认的具体行为

推荐采用“审核后提交并合并”：任务有未提交修改时，合并确认框明确显示会创建任务提交；干净且已有提交时只合并。另一方案是只合并已提交结果，但会让当前默认不自动提交的执行 Agent 留下的成果无法直接通过按钮集成。始终自动提交、自动合并会绕过用户确认，不采用。

本批采用普通 Git 合并：能快进时快进，历史分叉且无冲突时创建合并提交。不 squash、不 rebase、不推送；保留任务分支与 worktree 以便继续开发。任务的正常开发、消息发送和轮次结束均不会自动提交或合并。

## 1. 主分支默认值

添加项目无需新增必填项。后端按以下顺序识别本地目标：有效的本地 `origin/HEAD` 对应分支、`main`、`master`、项目当前非任务分支。仅本地读取，不 fetch、不访问远程。空仓库记录当前未诞生分支；新建仓库初始化时明确使用 `main`。

识别结果持久保存，避免之后切换项目目录分支改变合并目标。旧项目在首次检查时补齐；不把 `kaiwu/task-*` 或 detached HEAD 当成自动目标。无法识别时显示原因，并允许在项目高级设置中指定已有本地分支；不弹出所有项目都必须回答的选择向导。

项目高级设置提供可选的“主分支”覆盖项。修改目标后重新检查卡片，不更改任务已有分支、基线或文件。主分支被删除、重命名或目标不合法时显示“需核查”，不悄悄改用其他分支。

新任务 worktree 从已记录主分支的提交创建，而非项目目录恰好 checkout 的任意分支。已存在的任务保留原 worktree、分支与基线，不重建、不 reset；失败重试和服务重启继续校验原归属。

## 2. 卡片上的 Git 状态

保留右上角现有执行角标。在卡片底部增加一条小字 Git 状态，选中任务后的聊天顶部可查看目标分支、简短提交号、检查时间和阻塞原因，不展示源码或 diff。

| 状态 | 实际依据 |
| --- | --- |
| 未开始 | 尚无任务工作区 |
| 无改动 | 工作区干净，任务还没有相对于创建基线的新提交 |
| 待提交 | 存在已跟踪、暂存或未忽略的新文件修改；不能被“已合并”覆盖 |
| 未合并 | 有任务提交，当前任务 HEAD 不是目标主分支 HEAD 的祖先 |
| 已合并 | 工作区干净、有任务成果，当前任务 HEAD 可从主分支提交历史到达 |
| 需核查 | 工作区归属／路径／分支异常、目标缺失、Git 检查失败或状态无法可靠读取 |

“已合并”说明提交已纳入本地主分支历史，不代表已经推送、测试通过、用户验收或功能仍未被后续 revert。执行完成和合并成功不互相替代。

部分合并或部分 cherry-pick不能使整个卡片变绿；合并后新增提交恢复“未合并”，新增文件修改恢复“待提交”。外部 squash／rebase 可能不保留提交祖先关系，不能仅凭空 diff 或 Agent 回复认定“已合并”；界面说明未找到当前任务提交的完整合并记录。分支名相同、曾成功合并的回执、相似的补丁都不能覆盖当前 Git 检查结果。

存在冲突、未结束的 merge/rebase/cherry-pick、脏子模块等时展示具体原因并禁止产品合并。忽略文件不作为普通待提交文件；子模块与特殊文件不能通过静默过滤假装提交完成。

## 3. 合并按钮与聊天交互

- 卡片和任务聊天顶部使用小型合并图标，提供 tooltip、键盘焦点和可访问名称，与开始开发的播放图标风格一致。
- 未开始或无成果时不提供可执行合并；执行中显示禁用原因。已合并且无新增修改时不重复操作。
- 点击图标先请求只读预检，再打开确认框：任务、目标主分支、任务／主分支提交号、待提交文件数量及路径清单、提交说明、提交身份、冲突或阻塞原因。文件清单不展示内容或 diff。
- 有未提交文件时按钮写“提交并合并”，无未提交文件时写“合并到主分支”。提交说明默认采用卡片标题，允许修改。
- Git 提交身份默认读取项目本地 `user.name`／`user.email`；缺失时使用明确展示的服务身份 `Kaiwu <kaiwu@localhost>`，可以在高级设置中覆盖，不伪造用户身份或修改全局 Git 配置。
- 提交范围默认包含当前任务 worktree 内全部已跟踪修改及未忽略新文件，完整列出范围。遇到私密配置／密钥路径、新增嵌套仓库、未处理子模块等，阻止一键提交并提示处理；不静默漏文件后显示完整合并。既有已跟踪文件也检查敏感路径。
- 确认后操作由服务器持有；关闭确认框、换卡片、刷新或 WebSocket 断线不会取消 Git 操作。结果归属原任务，不弹到后来选中的任务。

任务聊天单独发送明确短语“合并到主分支”“提交并合并到主分支”（允许前缀“请”、末尾标点）时打开同一确认流程，不直接把这段话当作已执行 Git 的证据。否定句、问句、引用和更长描述作为普通对话；项目聊天没有明确任务目标时提示先选卡片。其他自然语言由既有 pi 对话处理，不能声称已实现任意语言的可靠意图识别。

无论外部 Git 命令由用户还是 pi 发出，状态检查仍读取同一套实际 Git 证据。通用 Agent 工具审批／沙箱不在本批；当前 bash 能力不是文件系统隔离，不能承诺它一定经过产品合并接口。

## 4. Go 执行边界与生命周期

增加集中 Git 检查／集成组件，复用现有 Go 进程、存储与工作区归属校验。前端仅显示服务端预检和提交明确确认请求，不能通过传入任意路径、分支或 SHA 执行命令。

服务端为同一 Git 公共目录的集成操作取得项目级独占锁，为目标任务取得任务写入保留权，顺序固定为项目锁后任务锁。保留期间拒绝该任务发送／恢复／开始开发；其他独立 worktree 的任务可以继续开发。同一仓库经多个项目入口登记也必须共享项目锁。

任务正在执行时不强行中断并合并。空闲 pi 仍持有工作区租约，合并前要停止并可靠回收该实例及进程组，保留原会话文件，再在没有其他存活写入者时接管租约。回收失败、崩溃后遗留写入者或锁归属不明则拒绝写入。合并后下一次用户发消息仍恢复同一 pi 会话，复验原 worktree，不重放开发请求。

确认请求携带预检标识；预检绑定任务、目标、两个 HEAD、工作区状态与文件内容指纹、提交范围和身份。取得锁并停止写入者后重新检查，变化时使预检过期，要求展示最新结果。不能仅使用应用 revision 判断外部 Git／文件是否变化。

## 5. 提交和合并步骤

1. 校验登录、同源、操作 ID、项目／任务归属、预检和写入保留权。将操作意图持久化，再产生 Git 副作用。
2. 检查项目目录当前 checkout 的就是目标主分支，且无已跟踪、未忽略新文件或未完成 Git 操作。目标分支在其他 worktree checkout 时明确指出位置，不自动 switch、不覆盖那个目录。项目目录不干净时阻止集成，不 stash、reset 或删除文件。
3. 验证任务 worktree 的 canonical path、Git common dir、owner 文件、任务分支和预期提交；不接受仅仅碰巧同名的分支。
4. 有待提交修改时按已确认范围创建普通任务提交，记录提交 SHA。提交失败停止；提交成功而后续合并失败时保留该提交和工作区，明确显示“已提交，尚未合并”，重试不重复提交相同结果。
5. 对固定提交进行合并预检。普通有共同祖先的分叉使用 `git merge-tree --write-tree` 检查冲突；无冲突再在主分支目录执行普通 merge，快进优先。调用禁用 hooks、交互编辑器、签名提示、远程凭据提示和自定义合并驱动，不执行用户 Git alias。若环境所需能力不可用，明确拒绝，不降级为盲目写入。
6. 执行前最后复核主分支 HEAD 和干净状态。实际 merge 仍可能受外部进程影响；Git 报错或冲突时保留现场与具体原因，不自动清除 Git 锁、abort、选择 ours/theirs 或声称没有副作用。
7. 成功后重新检查任务及主分支实际状态，记录结果和相关 SHA，发布 WebSocket 更新。提交成功的退出码或合并文字摘要本身不足以标记“已合并”。保留分支与 worktree，不 push。

空仓库允许继续现有无初始提交的任务开发，不为了建 worktree 自动提交。首次显式合并时，干净的未诞生主分支可以接收任务首个提交。若原项目尚有种子文件、未提交修改或其他独立根历史，显示具体阻塞原因与“请先处理项目初始版本／共同基线”，保留任务结果；不自动覆盖原文件、不偷偷创建主分支初始提交或强行合并无关历史。用户明确处理初始版本后可重新预检；本批不把这些需要人工集成的情况藏成成功。

## 6. 持久化、重试和更新

项目增加已识别主分支和可选覆盖值；旧 SQLite JSON 状态采用兼容缺省迁移。任务保存最新 Git 检查结果、时间与原因；合并操作另存阶段、授权预检摘要、期望／结果 SHA、错误和操作回执，不把布尔“已合并”作为事实来源。

合并不放进现有持有 Store 全局互斥锁的 `PreparedCommand.prepare` 内。先以短事务登记、保留操作，再由服务生命周期管理的工作单元执行，阶段更新用短事务提交；不让 Git 调用阻塞全部项目消息保存。

重复 operation ID 返回同一操作；同 ID 不同参数拒绝。浏览器丢响应可查询原操作，不能生成新 ID 自动重复 Git 副作用。服务重启核对已记录 SHA 和 Git 当前状态：可证实完成则补结果；可证实仅任务提交完成则保留待合并；中间状态不明显示“需核查”，不自动再次提交／合并。

活动项目每 3 秒触发一次合并状态检查，并在进入项目、窗口重新可见、任务执行结束、合并结束及手动刷新时检查；服务停止时取消检查。检查有并发与超时上限；结果变化才持久化并广播，避免不断增加 revision。无打开页面时不依赖后台轮询来保证 Git 操作完成；重新访问立即核对，不依赖数据库里旧的绿色状态。

## 7. 验收范围

使用临时 Git 仓库、隔离假 pi 和固定数据；不调用真实模型，不对当前开悟仓库提交／合并，不改变现有访问令牌、数据库或 7331 端口。

| 场景 | 必须证明的结果 |
| --- | --- |
| 默认主分支与高级覆盖 | 常见项目无需配置；覆盖可用，删除／歧义可见；已有任务不重建 |
| 两卡并行开发 | 分支／目录／会话互相隔离；两个合并串行，不妨碍其他卡片开发 |
| 未提交、新文件、暂存与敏感路径 | 正确待提交；审核范围完整；禁止漏文件后标完整成功 |
| 无改动、空仓库 | 初始相同 SHA 不标已合并；空目录首个结果可显式合并；种子文件阻塞有原因且保留 |
| 快进、普通分叉、冲突 | 前两者可集成；冲突不被自动解决或隐藏 |
| 按钮、聊天、外部 merge | 同一实际状态；聊天否定／问句不触发 Git |
| 部分合并／cherry-pick／squash | 不把部分成果标为全部合并；说明祖先关系的判断边界 |
| 合并后继续修改或提交、外部重置主分支 | 自动重新显示待处理，不用历史回执覆盖实际状态 |
| 主目录不干净／切到其他分支／操作未结束 | 拒绝集成，文件保留，不自动 stash／switch／reset |
| 执行中、闲置实例、遗留进程 | 执行中不合并；空闲可靠回收后继续原会话；遗留写入者阻断 |
| 重复点击、丢响应、过期预检 | 不重复副作用；外部改动后必须重新审核 |
| 重启、提交成功而合并失败 | 保留可核实结果和明确阶段，不偷偷重放 |
| 工作区被删／分支被换／路径重定向 | 需核查，不自动重建并掩盖成果丢失 |
| Web 与聊天回归 | 图标、键盘、窄屏、范围切换、Markdown、预览、WS 重连仍有效 |

最终维护 README／路线图及实际验证记录，区分已实现、测试证据和仍需人工处理的 Git 状态。PC 三平台、Android、未来团队协作与通用可配置编排方向保留，不纳入这批实现。

## 技术依据

- [Git merge](https://git-scm.com/docs/git-merge)：合并前检查、快进和冲突行为。
- [Git merge-base](https://git-scm.com/docs/git-merge-base)：`--is-ancestor` 判断提交可达关系。
- [Git merge-tree](https://git-scm.com/docs/git-merge-tree)：不更新工作区／索引的合并检查；写对象与执行实际 merge 仍须分别处理。
