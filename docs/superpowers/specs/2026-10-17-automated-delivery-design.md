# 固定开发交付流程与 GitHub Actions 自动修复

日期：2026-10-17。

状态：**用户于书面规格交付后回复“ok”，本规格已获审核；[实施计划](../plans/2026-10-17-automated-delivery.md)及串行实现方式亦已获审核，基础 Task 1、2 已实现；当前 Task 3 官方接口资料抓取受阻，产品闭环尚未完成，见[执行记录](../../development/web-automated-delivery-ledger.md)。** 本次只写文档，不授权对开悟当前仓库提交、合并、推送、创建工作流、运行真实模型或触发真实 Actions。文中的默认值是本规格提出的实施选择，随书面规格一起审核。

## 1. 需求与成功标准

用户希望统一产品模型：对用户而言是在“开发功能”，不应反复手动操作开发结束、提交、合并、Push 等技术步骤。流程按项目配置一次，任务沿用配置；推送后还要检查 GitHub Actions，代码导致的失败由 AI 自动修复并继续提交，直至通过或触及明确边界。

成功标准：

1. 一张卡片绑定独立分支、worktree 和原 pi 会话；不同功能可并行开发，同仓库主分支集成串行。
2. 正常路径用户只需表达开发意图；项目要求人工效果验收时，只保留一个业务确认节点，不逐项确认 Git 操作。
3. Go 服务执行可持久恢复的固定流程；AI 负责开发、诊断和修复，不凭 AI 的“已完成”声明跳过检查。
4. 本地检查、任务分支 CI、合并后主分支 CI 都有实际证据。精确 SHA 的所有必需检查通过才标记技术交付成功。
5. 代码问题可有限自动修复；权限、Secrets、冲突、来源不明的改动和不确定副作用停止并说明，不无限消耗模型或 CI 额度。
6. 页面仍然是专题看板＋右侧任务聊天，无源码/diff 展示，不变成 CI 控制台或 IDE。

### 1.1 方向与授权的区分

本规格讨论的是产品将来如何执行用户配置的持续授权，不是本开发会话获得了任意 Git、模型调用或发布权限。项目开启自动交付时，用户必须明确确认仓库、任务分支命名空间、目标主分支、允许的提交／合并／推送，以及这些推送会触发的检查或其他外部副作用。

此前的本地合并设计默认逐次审核、不推送；本规格获批并实现后，仅对**显式启用且任务有对应配置快照**的自动交付周期替换该行为。旧任务及未启用项目保留原行为，不能把既有任务的“完成”追溯解释为远程写入授权。

## 2. 当前事实与本批范围

已阅读的实际入口：

- `server/internal/agent/workspace.go`：首次开始开发从已识别本地主分支创建 `kaiwu/task-<taskID>` 与 `<DataDir>/worktrees/<taskID>/tree`，继续开发／恢复复用原工作区；不自动删除。
- `server/internal/agent/launch.go`：开发模式启用原任务 pi 的写入和 bash，当前系统指令禁止自动提交、合并、推送。
- `server/internal/agent/integration*.go`、`server/internal/gitops/`：本地审核、写入租约、Git common dir 集成锁、实际祖先关系及重启核查已有实现；旧合并操作重启不重放。
- `server/internal/workbench/`：项目、任务、轮次与结果验收、操作幂等和 SQLite 持久化已有基础。
- 正式业务通过 `/api/socket`，连接关闭不结束服务器任务。
- 当前开悟仓库没有 `.github/` 工作流目录；不把“能够查询 Actions”当作工作流已经存在或验证通过。
- 当前 Git 子进程禁用了全局 Git 配置且没有专门的远程凭据通道。不能直接宣称可以沿用用户所有 credential helper。

本批设计包含：固定自动交付状态机、项目配置与授权、远程 Git、GitHub Actions 观察、受限自动修复、状态与记录、恢复及验收方案。

不包含：PR、Tag、Release、自动部署、组织账户体系、GitHub App 安装平台、通用工作流编辑器、多执行节点、Codex、全功能工具沙箱、自动删除 worktree。PC 三平台和 Android 继续保留首版目标，本批不声称完成原生端适配。

## 3. 方案选择

| 方案 | 优点 | 问题与结论 |
| --- | --- | --- |
| 只加 Push 按钮并串联现有手动入口 | 改动较小 | 不解决反复点击、CI 修复和无人打开页面时继续执行的问题，不采用 |
| 让 pi 通过提示词自行提交、合并、检查 CI | 早期演示快 | 权限、重启、真实 SHA、无限重试和并发边界不可仅靠提示词保证，不采用 |
| Go 固定状态机＋原任务 pi 开发／修复 | 权限、证据、重试和生命周期明确 | 需要新增交付记录及远程适配；采用 |

只建设一条固定流程，项目配置参数，不做图形化节点编排，也不在每张卡片要求选择一种工作模式。

## 4. 项目配置、授权与快照

项目菜单把现有 Git 设置扩展为“开发与交付设置”。普通任务界面不增加必填 Git 字段。

| 配置 | 本规格建议 |
| --- | --- |
| `enabled` | 旧项目及新建项目初始关闭；完成配置和明确授权后开启，不自动从已有 origin 推断授权 |
| 仓库／主分支 | 沿用已识别主分支，核实选定 remote 唯一指向的 GitHub.com 仓库 ID、owner/repo、fetch/push 目标；支持 HTTPS、SSH 的明确形式 |
| 分支范围 | 仅该项目归属的 `kaiwu/task-*` 和已确认主分支；不推送 tags／其他 refs |
| 本地检查 | 配置一组 argv、工作目录相对路径、每项超时；至少一项必需检查，不把模型自行报告的测试作为替代 |
| GitHub 检查 | 分别配置任务分支／主分支必需 workflow ID，及可选必需 job 名称；两阶段均至少一个必需 workflow |
| 人工效果验收 | `requireAcceptance`，建议初始为 true；项目可明确改为 false。配置一次，任务不再反复选择模式 |
| 修复上限 | 每周期最多 3 次自动修复调用；本地、任务 CI、主分支 CI 共用额度，不各算 3 次 |
| 时间上限 | 自动活动累计 60 分钟；不计人工等待和调度排队，单次本地命令默认 5 分钟；超限转需要处理 |
| CI 等待 | 等待触发默认 5 分钟；每阶段排队＋运行默认 30 分钟；按项目可调，仍受总活动时间限制 |
| 凭据 | Git 远程凭据引用、GitHub API 凭据引用；不在配置快照保存 secret 本体 |

固定流程必须具备本地检查和两个 CI 门禁；若项目没有适用的 Actions，显示“交付配置未就绪”，允许继续已有本地开发／验收，不显示自动交付成功。创建或调整 workflow 是独立可审核的代码改动，不静默替项目补一份任意工作流。

必需 workflow 应对任务分支和主分支的 `push` 触发，并具有稳定 workflow ID；仅 `pull_request`、路径过滤导致不触发、环境审批或依赖手动触发的配置不能冒充适用。预检可以发现明显错误，但运行时仍以实际运行记录为准。此批不主动 dispatch／rerun workflow，不因观察失败而制造额外运行。

开启前明确提示：推送任务分支也会向 GitHub 上传代码并可能触发 workflow；主分支 push 可能触发部署、发包等。用户需确认该仓库的实际触发副作用属于授权范围；不能承诺服务只查询 CI 就能阻止仓库已有部署。未确认的发布／部署触发属于配置阻塞，不通过自动修复绕过。

启用配置增加 policy version、授权范围摘要、授权时间与操作者标识。现有单令牌认证只能记录本地登录身份，不伪称支持多人独立审计。任务首次显式开始本周期时保存不可变配置快照与模型配置，已有周期不追溯模板更改。检查命令、workflow/job 选择、主分支、仓库或权限范围变更只对新周期生效；活动周期需要改变时先暂停，明确采用新版本并形成新的审核记录，不能悄悄放宽门禁。

停用自动交付、撤销授权或凭据不可用对活动周期立即生效：不再启动新的外部副作用，已发出的操作先核查。模型凭据和 GitHub 凭据互不混用。

## 5. 固定流程与效果验收

```text
显式开始开发（保存配置快照与周期 ID）
  → 原卡片 pi 在独立 worktree 开发
  → Go 执行本地检查，失败可进入自动修复
  → 冻结改动指纹，创建任务提交
  → 推送该任务分支，等待该 SHA 的任务 CI
  → 进入项目 FIFO 集成队列
  → 同步最新可靠主分支基线；候选变化则重新检查、提交、任务 CI
  → 项目要求时：一次人工效果验收，绑定最终候选
  → 本地主分支接收已验证候选
  → 本地集成验证 → 推送主分支 → 主分支 CI
  → 技术交付成功
```

仅“开始开发”或任务中明确继续开发的新用户意图创建／继续授权周期；普通聊天、选卡片、打开页面、旧轮次结束、服务重启不会为没有授权周期的旧任务自动补提交或 Push。每任务只允许一个活动周期；交付后继续修改开启新周期，保留原 worktree、分支、会话和历史交付结果。

### 5.1 候选内容与检查证据

本地检查由服务器从快照配置启动并记录退出状态、命令标识、时间、输出摘要。以 argv 直接启动，不隐式拼 shell；工作目录解析后必须位于当前受管工作区。使用白名单环境、独立进程组、有界输出和退出回收，不继承服务凭据。固定当前文件／索引／HEAD 指纹，检查结束复核；代码改变则旧检查失效。构建产物应使用忽略目录，不把检查产生的未知源码修改静默纳入提交。提交后再次核对 tree 与已检查输入一致，不能先检查 A 再提交 B。

每次修复或同步主分支后重新执行全部必需检查；同内容重复提交不作为一次新修复成果。生成提交说明可以使用 AI 摘要，但 Go 负责实际提交及 SHA 核对，敏感路径／内容检查仍需通过。不得把 AI 对 CI 原因的判断当作退出状态证据。

### 5.2 人工效果验收

`requireAcceptance=true` 时，最终候选的本地检查和任务 CI 通过后显示“查看效果／验收并交付”；按钮授权继续当前周期的技术交付，不再逐项弹提交、合并、Push 确认。为了先验证 CI，任务分支在效果验收前已推送，此点必须在项目授权中明确展示。

验收令牌绑定 delivery ID、候选 SHA／tree、主分支基线及最新成果轮次，不复用当前仅绑定旧轮次的确认作为无限期批准。候选源码变化使旧验收过期，需要再次看效果；纯观察或同 SHA 的查询重试不要求再次验收。主分支 CI 修复造成源码变化时同理，属于异常路径重新验收而非每个 Git 步骤确认。

`requireAcceptance=false` 时技术门禁通过就自动推进；界面明确“未人工验收”，不伪造用户点击或替用户标记轮次已认可。功能认可、技术交付、实际 Git 状态分别记录，即使自动流程失败也不抹掉已有功能验收。

## 6. Worktree、主分支与并发集成

每卡片沿用现有独立 worktree、`kaiwu/task-<taskID>`、owner 文件和原 pi 会话。同卡片的修复不另建第二个执行会话，不向其他卡片注入上下文。任何进程启动、提交前仍核验 canonical path、Git common dir、分支、owner、预期 HEAD 和写入租约。

worktree 隔离的是文件和索引，不保证消除合并冲突或隔离端口、数据库、外部服务；测试需使用项目配置的隔离资源。当前 Linux 进程组／flock 的平台限制保留，未经验证的平台不悄悄降级为无保护并行。

### 6.1 集成队列和锁

- 队列以 canonical Git common dir 识别本地共享仓库；另以 GitHub repository ID＋目标主分支约束远程写入，避免同一服务中的重复登记或独立 clone 同时发布到同一个目标。
- 一个任务初次任务 CI 通过后取得 FIFO 队列票据。轮到队首后保留逻辑集成槽，直到主分支 CI 通过或明确终止。其他任务可继续在各自工作区开发、检查和推送任务分支。
- 等待 CI、人工验收、模型修复时不长期持有 OS 写锁。逻辑槽持久化；实际 Git 变更按固定顺序取得远程目标门、项目 common dir 锁、目标任务写入租约，再短时执行，避免锁反转。
- 同一 worktree 永远只有一个写入者。pi、检查进程、提交／合并、受控预览之间显式交接；沿用停止空闲 pi、保留 session、回收进程组的规则。CI 等待期间可释放 OS 租约，但普通新消息若会修改候选，须先暂停周期并使检查失效；只读查看不影响流程。
- 自动交付活跃时禁止旧手动合并接口并行绕过队列；未启用项目保留原审核入口。服务无法拦截外部 Git，故每次变更前复核实际 HEAD／refs／工作区。

### 6.2 同步与合并策略

启用配置及创建新任务前检查本地／远程主分支。仅在干净目录、身份可靠且是预期快进时可同步已授权主分支；不 clone、stash、reset、rebase、强推或强行合并无关历史。已有本地领先提交必须能归属受管理的交付操作，否则阻塞，不能顺手把其他人的本地提交上传。远程缺失／空仓库在初次配置时明确说明是否允许创建主分支，未授权不创建。

队首重新读取远程主分支，核对其与本地主分支关系。候选落后时，由 Go 在干净任务分支普通合并最新可靠主分支，保留历史，随后重跑本地检查、推送任务分支并等待新的任务 CI。冲突直接转需要处理，不自动选择 ours/theirs，不让模型凭空决定另一个功能应被覆盖。

集成主分支时优先保证已验证任务候选包含当前主分支，因而主分支可快进到同一 SHA；这样不能用合并前某个 SHA 的绿灯冒充另一个合并提交的绿灯。若主分支再次改变，重新生成候选与门禁，不盲目普通合并后沿用旧证据。主目录 checkout、干净状态和未完成 Git 操作等保护沿用旧实现；不自动切换用户目录分支。

主分支推进后再执行配置的集成检查，绑定实际主分支 SHA；失败则保留本地未推送状态并修复，不偷偷 reset。通过后仅推送精确已核验 SHA 到明确目标 ref，禁止 mirror、tags、默认 refspec、任意 `pushurl` 或多目标 push。即使有竞争，远程普通快进检查也必须拒绝覆盖他人历史。

### 6.3 主分支失败后的修复

本地集成检查或远程主分支 CI 失败时，当前周期继续占据逻辑集成槽，阻止后续任务把新功能叠到失败基线上。界面明确“主分支已推送，CI 未通过”或“仅本地已集成，尚未推送”，不标已交付。

恢复原任务 pi 之前，Go 在干净原任务分支纳入本周期已集成的主分支 SHA，再将确切失败证据交给原会话。AI 只改原任务 worktree；修复生成新提交，重新经过本地检查、任务 CI、必要的效果验收、快进集成、Push 和主分支 CI。保留原失败提交和运行记录，不自动回滚远程历史。

如果主分支被外部推进、任务 worktree 有未归属修改或无法确认失败归属，停止自动修复，不把其他任务失败算到当前任务。阻塞时保留集成隔离状态；用户可明确终止周期并解除队列，但要展示主分支仍未验证，不能把解除阻塞标作 CI 通过。后续自动交付前必须重新确认可用基线。

## 7. GitHub Actions 观察与结果判定

新增纯 Go GitHub REST 适配，首批只支持 GitHub.com。使用服务持有的受限 API 凭据，服务主动轮询，不依赖浏览器轮询，不引入公网 webhook、`gh` 宿主或新语言后端。

每阶段绑定 repository ID、分支、commit SHA、event=`push`、必需 workflow ID，保存 run ID、run attempt、创建时间、状态、conclusion 和真实 GitHub 链接。查询使用 SHA 条件，必要时分页并再次逐条匹配，不能只读“仓库最近一次 CI”。同 SHA 多分支／多个 workflow／旧 rerun 不能互相替代。GitHub API 版本在实施时核对并固定，不在本规格凭搜索摘要猜定版本。

| 结果 | 固定处理 |
| --- | --- |
| queued／in_progress 等未结束状态 | 等待，在持久截止时间内退避查询 |
| 必需 workflow completed＋success | 该 workflow 通过；全部必需项通过才放行 |
| failure | 获取失败 job／step 与有界日志，进入分类；可修代码问题才消耗修复额度 |
| cancelled／timed_out／action_required／stale | 不通过；显示取消、超时或人工审批等原因，不自动伪装修复 |
| skipped／neutral | 首批不作为必需 workflow 成功，不按空集合推导通过 |
| 没有对应运行／workflow 被禁用／仅 PR 触发 | 等待触发窗口后配置阻塞，不自动转为无需 CI |
| 401／403／404、额度不足、API 限流 | 区分认证、授权／不可见、资源缺失与限流；不当作源码错误 |
| 连接错误／5xx | 有界退避，恢复后重查原 SHA，不重复 Push 或创建修复提交 |

如果配置了必需 job，则还需在选中 run attempt 的全部分页 jobs 中找到对应 job 并明确成功，workflow 总体 success 不能掩盖该 job 被条件跳过。默认仅 workflow 级门禁，项目可明确配置 job；矩阵项目需选定稳定且完整的 job 名称集合。不会自动把 GitHub 的分支保护成功语义等同于本产品更严格的门禁。

默认查询间隔约 10 秒，并做抖动、ETag／条件请求和服务级并发上限；按 `Retry-After`／限流头退避。以已保存的截止时间控制等待，不因重启重新获得完整等待时长。API 请求默认 15 秒超时，输出、页数和查询频率有界；无法完整检查必需结果时阻塞，不截断后假通过。

普通分支 push 才是触发入口。认证方案不能误用导致递归抑制的 Actions `GITHUB_TOKEN` 并声称一定触发 CI；实际没有运行仍按缺失处理。晚到的旧 SHA 结果只更新旧历史，不推动当前候选。观察到人工 rerun 时跟踪最新 attempt，旧失败不覆盖新 attempt，旧成功也不覆盖新失败。

交付成功绑定最后一次发布 SHA；完成前再次确认远程主分支仍为本周期已验证目标、任务结果完整可达。外部又产生新提交时标记“主分支已变化，需核查”，不能把 A 的绿灯挂到 B 上。已完成交付保留历史 SHA 和当时证据，后续分支变化不篡改历史记录。

## 8. 自动修复循环与额度

进入修复前持久记录 repair attempt、触发阶段、失败 SHA／run attempt、日志摘要指纹、剩余额度及允许范围。每次实际向模型发出自动修复请求前原子扣减额度；请求结果不明时不自动以新 ID 重发。一次修复请求结束后必须再次观察真实文件与检查结果。

AI 输入包括原始功能要求、当前候选、Go 检查出的失败步骤和脱敏日志，不包含 GitHub 凭据。系统生成的修复轮次在任务聊天明确标注“系统自动修复 · 第 N/3 次”，不是伪造用户消息；服务端以持久 job ID 发起。与原会话历史隔离规则一致，不创建第二个任务执行会话。

仅显式授权周期内可由服务产生这些新轮次；这扩展的是自动交付的持续意图，不改变“没有新意图不重发旧开发指令”的默认恢复规则。调用原 pi 仍需通过既有进程归属、session 文件和最多 8 个实例的容量限制；容量不足排队，不并发抢写、不默认再派生 Agent。模型初值取任务配置快照；用户在任务内显式改模型仍按已有规则从下一轮调用生效，不回写项目模板、不打断正在运行的请求。自动修复使用该任务当时有效的模型，并记录实际 provider/model，不借自动化新增运行时 Agent 类型切换。

允许自动处理编译错误、测试断言失败、类型／格式问题等有具体源码证据的问题。基础设施／供应商偶发错误先有界观察，不能靠新空提交反复触发 CI。原因不确定、缺少凭据／Secrets、环境审批、额度不足、Git 冲突、分支保护要求 PR 时需要用户处理，不绕过保护。

以下行为不能作为自动修复：删除失败测试、降低断言、删依赖的检查、写 `[skip ci]`、缩小 required workflows/jobs、改权限／Secrets、扩大发布范围、改远程目标或强推。workflow 文件和项目检查／授权设置的变化是保护范围，启动周期时冻结相关定义指纹，自动周期发现变化后暂停审核，不能在同一周期降低门禁。检查脚本及测试文件的修改需提供合理依据与实际复验；服务可以机械阻止明显禁用规则，但不声称能自动证明任意测试修改没有削弱语义。

连续相同失败指纹且没有有效源码变更、出现越权改动、达到 3 次、超过时间上限时停止。达到上限后的“继续处理”必须由用户明确发起新的有限额度，不能刷新页面或重启自动清零。启动自动模式时说明会使用模型和 Actions 配额；首次真实联调仍单独说明并取得本次执行授权。

## 9. 凭据、远程命令和日志安全

Git 与 REST 使用分开的受限接口：

- 首批 API 凭据引用来自服务器受保护环境配置，不保存到 SQLite／浏览器 localStorage／任务快照；校验所选仓库可见和 Actions 读取权限。Git HTTPS 写入需要对应 Contents 写权限，SSH 写入使用服务明确允许的 key／agent 引用；两者能力分别检查，不以 API 可读推断 Git 可写。启用前只做无写入的配置／读取预检，不能为探测权限创建提交或临时远程 ref；最终写入权限及分支保护以已授权的实际 push 结果为准。
- 凭据只注入固定远程子进程或 Go HTTP 请求，不给 pi、测试命令、预览进程。HTTPS 使用临时受控 askpass／credential 桥，仅为冻结的 HTTPS GitHub 地址提供凭据，不通过 argv、URL、日志暴露 token；SSH 使用固定 host、既有 known_hosts 和非交互模式，不自动信任新 host key。
- 不重新开放全部个人全局 Git 配置、任意 credential helper、alias、hooks、签名提示和自定义 merge driver。只有显式白名单凭据路径／环境可进入远程操作。
- 不直接使用仓库中可能被修改的 remote 名称作为可信目的地。授权冻结标准化 URL 与仓库 ID；拒绝带凭据 URL、额外 pushurl、URL rewrite、任意协议、外部 remote helper 和不匹配目标。fetch 限定目标 ref、禁止隐式跟随 tags，push 使用固定单 refspec；网络操作单独采用有界超时与进程组回收，而非照搬当前本地 20 秒超时。
- GitHub API 请求只发往固定 API 主机。下载日志的跳转不携带 GitHub Authorization 到其他主机；临时链接只在受控 HTTP 客户端中使用，不暴露为任意 URL 抓取能力。

日志是来自仓库／CI 的不可信数据，不能当作新的系统指令或授权。先脱敏、截取失败上下文，再提供给 AI；禁止按日志要求读取密钥、上传环境或运行未知远程脚本。GitHub 的 secret masking 不等于日志无密钥；本地再做脱敏并提供人工处理路径。

初版优先按失败 job 获取文本日志，不递归解压任意归档。单阶段日志累计读取上限 8 MiB，交给模型的脱敏摘要最多 64 KiB，保存的阶段摘要最多 256 KiB；截断明确标注，证据不足不编造原因。原始凭据／临时下载 URL 不落产品记录。

现有 pi bash 和执行项目测试不是 OS 沙箱：恶意项目代码仍可能访问同机资源。上述凭据不注入、路径校验与固定命令是降低风险的执行边界，不承诺完整隔离恶意本机代码；正式用于不可信仓库需另行设计系统隔离。

## 10. 模块、数据与接口边界

新增职责建议：

| 模块 | 职责 |
| --- | --- |
| `server/internal/delivery/` | 固定状态机、调度／逻辑队列、预算、恢复、门禁和暂停／继续；不实现任意节点引擎 |
| `server/internal/githubactions/` | 仓库身份、workflow／run／job／日志的只读 Go REST 访问、退避与脱敏；不拥有模型会话 |
| `server/internal/gitops/` | 固定目标 fetch／push、候选同步、精确 SHA 检查，复用安全 Git 调用与租约归属 |
| `server/internal/agent/` | 原 pi 会话开发／修复、任务写入权交接、轮次落库和实际 settled 观察 |
| `server/internal/workbench/` | 配置与授权快照、交付记录及事务性阶段迁移；不在 Store 全局锁内运行 Git／网络／模型 |
| `server/internal/httpapi/`、Vue | 认证命令、状态／事件投影、配置和简洁任务进展 |

通过窄接口连接模块，delivery 编排 agent 能力，agent 的轮次通知只发布可持久消费事件，不反向导入 delivery。原 `MergeOperation` 仍代表旧手动合并事实；自动流程复用低层检查／执行能力，不能伪造一个“用户点击审核”的 MergePreview 绕过授权语义。

### 10.1 持久数据

- `ProjectDeliveryPolicy`：版本、目标仓库身份／refs、本地检查、必需 workflow/job、验收规则、预算、凭据引用、授权摘要／撤销时间。
- `Delivery`：ID、taskID、cycle、policy snapshot、触发意图 ID、phase、candidate SHA/tree、base main SHA、本地／远程 main SHA、验收令牌、repair 计数、截止时间、阻塞原因和版本。
- `DeliveryStep`：确定的 step ID、输入指纹、预期 refs、执行意图、归属进程、结果 SHA／退出码／有界证据。一个 step 只接受同指纹重试。
- `CIRunObservation`：repo/ref/SHA/workflow/run/attempt/job、状态、conclusion、链接、更新时间；新观察只影响对应候选。
- `DeliveryQueueEntry`：仓库／远程目标键、票据、逻辑占有者、隔离原因；多项目入口共享一致的写入门。

新增交付与步骤采用独立 SQLite 表和短事务，幂等 operations 与状态投影协调提交；不要把全部 CI 日志塞进现有全量 JSON 状态／WS 快照。迁移兼容旧数据，旧任务 delivery 为空不自动启动。快照只投影最新摘要和最近 20 条步骤，历史分页，沿用现有分块同步和缺口恢复。

### 10.2 状态机

内部阶段：`queued → developing → local_checking → committing → pushing_task → task_ci → preparing_integration → awaiting_acceptance? → integrating → integration_checking → pushing_main → main_ci → succeeded`。

失败可进入 `repairing` 再回 `local_checking`；`blocked` 记录可操作原因及是否占有集成槽；用户暂停为 `paused`；归属／副作用不确定为 `needs_check`；明确停止且核实写入者结束后为 `cancelled`。`succeeded` 不等于轮次人工确认。

开发轮次 settled 只使状态机评估后续检查，不能直接标 succeeded；恢复连接本身不生成开发结果。每步推进需 CAS 版本、当前授权和精确证据，重复消息不能重复消费一轮修复额度。

### 10.3 业务接口

沿用已认证 `/api/socket` 的命令／回执／事件，不新增浏览器直连 GitHub：

- 更新／预检／启用或撤销项目交付配置；预检返回能力与阻塞原因，不产生提交或 push。
- 开始／继续开发沿用原任务入口，由服务绑定 delivery ID 与快照，不要求前端拼装 Git 参数。
- 查询周期、分页步骤；确认最终候选效果；暂停、恢复明确阻塞、终止周期。

所有变更带 operationId 和必要的预期版本，服务根据项目／任务归属解析路径、refs 与凭据引用，拒绝任意客户端命令、SHA 或路径代执行。HTTP 仍用于初次认证／身份检查，业务通道失联不重放变更。

## 11. 生命周期、崩溃与恢复

服务器持有任务和 CI 观察生命周期；关闭浏览器、切卡片、WS 断开不终止流程。服务优雅停止时停止接收新步骤、持久化阶段并取消／回收自有本地进程；不因停止服务取消已在 GitHub 运行的 Actions。

每个副作用先记录意图与精确输入，再执行并记录证据。没有通用跨 Git／GitHub／SQLite 的 exactly-once 事务，必须逐步核查：

| 中断位置 | 恢复规则 |
| --- | --- |
| 本地检查／AI 请求执行中 | 先核验原写入者及结果；不自动重发旧模型请求。可证明已结束则消费现有结果，不明则需要处理 |
| 提交前后、回执未保存 | 核查预期 parent/tree、实际 HEAD 和归属；只有唯一匹配成果才补记，否则 needs_check，不盲目再 commit |
| task/main push 结果未知 | 查询实际远程 ref／fetch 所需证据；远端已到目标或有明确可达关系时补记，不凭网络错误认定未推送 |
| 明确尚未执行的下一步 | 授权仍有效且前置证据／refs 未变时可自动继续，不新增用户意图 |
| CI 等待 | 恢复原 SHA、run/attempt 和截止时间的只读观察，不重新 push／dispatch |
| 已集成但 CI 未通过 | 恢复逻辑隔离槽与真实阶段，不能放行下一任务；满足修复条件且有明确新修复 job 时继续 |
| 未知进程／锁／外部改动 | 保留工作区与记录，needs_check，不按数据库 PID 盲杀、不清 Git 锁、不删除现场 |

远程 ref 已被其他写入者改变时，不自动把当前 ref 当作原目标成功；需要区分本周期提交可达、本周期 SHA 的 CI 和当前主分支状态。无法证明当前门禁仍成立则暂停。

自动恢复只延续已持久授权周期中可证明安全的下一步，不更改旧手动合并的“只核查、不重放”约定。暂停／终止先停止后续调度，等待正在发出的操作核查完毕；不能用浏览器取消假装撤销已经推送的提交。

## 12. 页面表现与兼容

专题归属不改变，右侧仍是原任务聊天。交付阶段投影为“开发中／验证中／自动修复中／等待验收／等待集成／需要处理／已交付”，不把它们变为看板固定列。

保留现有开发／结果／中断状态；增加轻量交付摘要，不把 `Delivery.phase` 直接写入旧 `Task.status` 导致旧客户端失效。卡片优先显示当前动作，详情可区分功能验收、连接状态、Git 与 CI。

- 正常只保留开始／查看效果及项目要求时的验收；提交、合并、Push 显示为过程记录，不是必点按钮。
- 显示真实失败步骤、自动修复次数、当前 SHA、Actions 链接；手机默认收起技术细节。
- Git 已合并但 CI 红灯必须可见；不只显示“已完成”。无 Actions 配置明确提示未启用自动交付。
- 用户继续修改当前候选时先暂停流程、失效相关检查，可靠接回原会话，不与服务器提交竞争。
- 旧项目／旧结果保持原本地验收与审核入口，设置引导不能强制重新创建项目或任务。
- 不自动回收任务分支、worktree、历史会话或预览成果；不把本设计变为 Paseo Workspace 自动创建授权。

## 13. 验收矩阵与实施分层

先用临时 Git 仓库／bare remote、Go 假 GitHub HTTP 服务、隔离假 pi 做确定性验证。测试绝不对开悟当前 checkout 提交／合并，不向真实 GitHub 写入，不加载个人扩展。

| 场景 | 必须证明 |
| --- | --- |
| 配置及授权 | 无授权不上传代码；版本快照不追溯；撤销立即阻止下一副作用；旧任务不自动启动 |
| worktree 和会话 | 两卡目录／索引／上下文隔离，同卡修复保留原 session，无第二写入者 |
| 正常闭环 | 本地检查、任务分支 push／CI、验收配置、集成、主 push／CI 按真实证据推进 |
| 检查绑定 | 文件变化、索引变化、主分支变动使旧绿灯／验收失效；提交 tree 与受测内容一致 |
| 精确 CI | 错 SHA／分支／event／workflow／attempt、晚到结果不放行；分页完整，缺失不等于通过 |
| workflow/job 语义 | skipped、neutral、取消、超时、未触发、必需 job 被跳过均不能冒充成功 |
| 凭据与网络 | REST 可读不等于 Git 可写；缺权限、Secrets、限流、5xx 分类；不因瞬断重复 push |
| 修复循环 | 失败证据交回原会话，修复后全流程重验，共用 3 次额度；相同无效循环停止 |
| 主分支失败 | 队列隔离，不叠加其他任务；原 worktree 修复产生后续普通提交，保留失败历史 |
| 并发／外部 Git | 同 common dir、多项目登记、同远程多 clone 互斥；外部 refs 变化阻断；未知本地提交不上传 |
| 审核与攻击输入 | workflow／门禁降级、带凭据 URL、多 pushurl、日志注入和 secret 泄漏被阻止或明确转人工 |
| 崩溃故障注入 | 每阶段意图／执行／回执窗口；不重复 commit／push／模型请求、不遗失队列槽和预算 |
| 客户端生命周期 | 换卡、断网、关闭、重连、重启不误杀任务、不重放操作，历史分页有界 |
| 兼容 | 原本地开发、预览、结果确认、手动合并、Markdown、手机布局和既有数据均回归 |

实施计划应拆成可验收的基础层（配置／存储／只读远程能力）、执行层（受控远程 Git／固定流程）、闭环层（CI／修复／恢复）、界面与集成验收，不把某一层完成宣称为整条功能可用。

真实联调在自动化通过后另行说明费用和副作用，使用用户明确批准的测试仓库／分支与受限凭据。分别记录真实 Git push、真实 Actions 触发及查询、真实模型修复、完整闭环；fake 结果不能替代真实能力。7331 服务保持现有版本，只有获批实施及部署时才更新，不因写文档重启。
