# AI 与用户的标准交互设计

状态：用户已整体评审并回复“ok”，批准按本方案推进实现。实施计划见 `../plans/2026-10-18-agent-user-interaction.md`；开发、测试及部署状态单独记录，不因设计批准视为已完成产品或真实模型验证。

## 1. 目标与现有事实

用户要求：AI 不仅会请求确认，也会要求输入、选择等；采用标准通用的交互方式，限定在所属任务的 AI 聊天内，而非全应用弹窗。每个任务独立。

现有实现：

- `apps/web/src/ProgressCard.vue` 将 `report.question` 渲染为“需要你决定”的只读提示，没有结构化答复和处理状态；选择历史轮次也会显示该轮问题。
- `server/internal/workbench/report.go` 严格解析 `<kaiwu-report>`，问题只有字符串字段。
- `server/internal/agent/events.go` 主要消费消息、工具与结束事件，尚未把 `extension_ui_request` 接入产品交互。
- `server/internal/pirpc/requests.go` 的普通 `Call` 明确不支持 `extension_ui_response`，不能以普通 RPC 命令冒充原请求响应。

目标是一个有生命周期的“用户交互请求”，而不是按正文问号猜测弹窗。统一产品协议与渲染，不引入自有 pi TypeScript 扩展、不额外调用模型总结或生成表单。

## 2. 方案选择与推荐

| 方案 | 优点 | 问题 |
| --- | --- | --- |
| 根据聊天文字自动识别问句并生成按钮 | 表面改动少 | 易误报、凭空编造选项、历史重复弹出、无法可靠关联答案；不采用 |
| 只支持 pi 原生交互事件 | 可精确回应真正等待中的调用 | 普通 AI 澄清问题不会自动成为这类事件，现有禁用个人扩展的启动方式也不保证存在来源；不作为唯一入口 |
| 统一交互协议，按来源适配 | 普通询问与真实 RPC 交互使用同一 UI，状态与能力边界清晰 | 需实现持久化、回复关联与适配；推荐 |

首先打通当前可用的“结构化提问—原会话新消息续接”闭环，再独立接入经版本核验的 pi 原生交互。后续原生端复用协议；本轮不新增原生端工程，也不扩展为通用编排引擎。

## 3. 统一交互模型

统一名称：**待你处理**。交互卡片明确显示“需要确认”“请补充信息”“请选择”等具体标题，不把所有请求都称为确认。

一份请求包含一个或多个字段；不是为每种组合分别设计一个弹窗。

| 字段类型 | 交互方式 | 规则 |
| --- | --- | --- |
| `confirm` | 明确的两个决定，例如“允许／不允许” | 无默认勾选；否定也是有效答案，不是关闭窗口 |
| `text` | 单行输入 | 标题、说明、占位符、必填与长度限制 |
| `textarea` | 多行输入 | 适合环境说明、要求与补充信息；不等于代码编辑器 |
| `single_select` | 单选列表 | 选项可带解释和推荐标识，不默认替用户选择 |
| `multi_select` | 多选列表 | 明确最少／最多选择数 |
| `number` | 数字输入 | 明确单位、整数／小数、最小／最大值 |

多个字段组合就是小表单，例如“选择部署环境＋填写访问地址＋补充说明”。首版保持以上有界字段，不做任意表单脚本、嵌套数组、动态条件表达式、附件或文件上传。日期等未来按真实需要增加类型。

选择题可显式开启“其他”，展开补充输入；选择“其他”后需填写说明，不凭空为上游请求添加其无法接受的选项。所有类型允许可选的普通补充说明，但原生适配不支持时必须显示能力限制，不悄悄丢弃。

只有 Agent 提供了明确选择项才显示选项。旧问题或不明确的提问一律采用自由文本，不从“是否”推断成具有授权意义的确认。

## 4. 聊天内的呈现与操作

### 4.1 默认呈现

- 当前可见会话收到有效新请求，在聊天底部、输入区上方展开局部交互卡片，视觉上类似局部 dialog；不使用全局 `showModal`、全屏遮罩或把弹窗挂到 body。
- 桌面不遮住看板、任务切换、聊天标题和已有消息；手机限制卡片高度、内容内部滚动，仍保留返回和收起入口，不弹全屏窗口。
- 展示所属任务、问题、必要原因、字段和操作。长上下文按需展开，支持现有安全 Markdown，不允许注入 HTML 控件或执行脚本。
- 使用非模态 dialog 语义及关联标题，不设置 `aria-modal=true`，不把整个应用 inert，不使用全应用焦点圈禁。仍可操作看板和其他任务。
- 新请求不抢走用户正在使用的输入焦点；通过可访问状态提示到达。用户主动打开时聚焦首字段，关闭时恢复合理焦点。非当前任务只更新其“待你处理”角标，不弹出、不抢导航。

### 4.2 操作语义

底部主要操作为“发送答复”；确认题使用明确的决定项，然后提交。表单统一一次提交，避免点选即触发，也避免键盘误确认。

- **发送答复**：校验后提交当前请求的全部必填项，只作用于绑定会话。
- **稍后处理／收起／Esc**：仅收起卡片，保留待处理入口与草稿，不向 Agent 发送同意、拒绝或取消。
- **拒绝／不同意**：确认题的真实否定答案，提交后按该来源的答复语义处理。
- **取消本次请求**：仅当来源明确支持取消时显示，说明这是取消询问而不是停止整个任务；不可用时不提供虚假按钮。

提交中防重复点击，失败保留输入并说明原因，收到服务端持久回执后才显示“已记录答复”；仅 Agent 已接受才显示“已发送给 AI”。失联或未知状态显示“答复已记录，送达待核查”，不能直接宣称已继续执行。

普通输入区在交互展开时收起为“改用聊天说明”入口；关闭卡片后仍可发一般消息，但**一般消息不自动消除待处理请求**。如用户要用自由文本替代表单，应选择“改用文字回答本次问题”，作为同一请求的替代答复提交，而不是依靠 AI 猜测是否已回答；仅对支持该形式的来源提供。

### 4.3 任务切换、排队与草稿

- 切到任务 B 时立即隐藏任务 A 的卡片；返回 A 可继续处理。不停止 A，不把 A 的答案发给 B。
- 同一会话一次主动展示一份请求；多个相关问题应组合一份表单。不相关请求排队，显示待处理数量，不叠多个弹窗。
- 发送时捕获请求及会话 ID，不读取点击后可能已经改变的“当前选中任务”。
- 待处理请求与已提交答复由服务端持久化，刷新／换设备后可恢复；未提交的普通草稿按会话＋请求＋版本在当前浏览器会话内隔离保存，刷新恢复，退出登录清理，不跨设备同步。
- 新请求首次到达可自动展开一次；用户手动收起后不因增量同步反复展开。切回任务显示明确待处理入口，不强制抢焦点。

### 4.4 历史

聊天保留问题、所选值／输入值、提交时间与状态，已完成交互折叠为简短摘要，可展开查看。

历史轮次只能查看历史交互；查看旧报告不能激活旧弹窗。与当前请求不匹配的旧答复按钮不可提交。

## 5. 状态、版本与生命周期

请求状态：

`pending → answered | cancelled | expired | superseded`

答复送达状态独立：

`recorded → dispatching → accepted | not_sent | uncertain`

- 关闭／收起不是请求状态变更；不会将 pending 改成 cancelled。
- `answered` 只表示答复已持久保存，不表示 Agent 已继续，更不表示任务完成。
- Agent 产生新版本时，旧版设为 superseded；旧设备提交旧版应明确冲突，不接受旧选项。
- 新问题是否替代旧问题必须有显式请求身份或替代关系；不能因为 AI 又发了一条消息就自动撤销所有旧问题。
- 请求可有明确截止时间，默认无倒计时；超时只能失效或按上游取消契约处理，不能默认同意或自动选择推荐项。
- 相同客户端 operationId 返回原回执；不同设备同时答复以第一次成功写入为准，后一次显示已被处理，不覆盖。

### 执行状态要分开

任务卡片增加面向用户的“待你处理”展示，与“待验收”明确区分。底层分别记录进程运行状态、是否存在阻塞型交互、成果验收状态和 Git 状态，不用一个枚举承担全部含义。

阻塞型请求使依赖答案的后续开发／自动交付暂停；其他任务继续。普通来源的请求必须在可确认的轮次结束边界发布为可回答状态，不能仅检测到流式 JSON 就声称 Agent 已经暂停或立即启动下一轮。请求产生前已经发生的工具执行不会被倒退，不能把这层交互宣称为系统级工具审批。

尚有阻塞型问题时，不显示“开发结束可确认完成”，也不自动启动修复、提交、集成或推送。与原自动交付状态机在服务端设置明确门禁，不能只禁用浏览器按钮。等待用户不计为模型正在运行；不能依靠断开客户端来停止任务或释放写权。

首版用户请求默认阻塞其后续流程；非阻塞“随时建议”仍使用普通聊天，不为了通知而弹交互卡片。

## 6. 通用协议

产品对象与 pi 原始事件分开。服务端生成可信请求 ID、归属和版本，不接受 AI 或浏览器决定项目／任务路由。

请求最小字段：

- `schemaVersion`、`id`、`version`。
- `projectId`、`conversationId`、可选 `taskId`、`roundId`、`sourceMessageId`。
- `source`：`assistant_question`、`agent_ui` 或 `system_action`；普通 AI 不能自报为可信系统操作。
- `title`、`description`、`fields`、`blocking`、`allowCancel`、`status`、时间信息。
- `sourceRef`：由服务端维护的上游关联；原生请求必须绑定进程运行代次及上游请求 ID，不能只绑定容易重用的 ID。

字段含 `id/type/label/description/required` 及白名单约束。选项使用稳定 ID 和展示文案，值按类型保存，不用显示顺序作值。

答复命令包含 `operationId/requestId/requestVersion/conversationId/answers/comment`；服务端核验归属、会话权限、字段类型、必填项、选项 ID、数量、大小和状态，拒绝未知字段与超限载荷。没有通用“执行这个命令”或自定义回调 URL 字段。

示例，仅为协议提案，不是当前已有 API：

```json
{
  "schemaVersion": 1,
  "title": "确认访问环境",
  "fields": [
    {
      "id": "network",
      "type": "single_select",
      "label": "访问设备的网络环境",
      "required": true,
      "options": [
        {"id": "same_lan", "label": "与服务器在同一局域网"},
        {"id": "vpn", "label": "通过 VPN 访问"},
        {"id": "unknown", "label": "不确定"}
      ]
    },
    {
      "id": "reachable",
      "type": "single_select",
      "label": "能否打开指定服务地址？",
      "required": true,
      "options": [
        {"id": "yes", "label": "可以打开"},
        {"id": "no", "label": "无法打开"},
        {"id": "untested", "label": "尚未测试"}
      ]
    },
    {"id": "details", "type": "textarea", "label": "错误现象或补充说明", "required": false}
  ]
}
```

具体上限在实施前固定并前后端一致校验，建议每请求最多 12 个字段、每选择字段最多 20 个选项、请求与答复各不超过 32 KiB；在现有 Socket 消息上限内传输。说明／字段内容不得充当服务端指令。

沿用 `/api/socket` 的认证、Origin 检查、operationId、增量与分块快照；新增交互命令与状态，不增加另一套 WebSocket 或全局事件总线。

## 7. 三种来源的处理

### A. 普通 AI 提问：当前首要闭环

Agent 按白名单结构输出专门交互块，例如 `<kaiwu-interaction>`，描述问题和字段。与进展报告分离，使普通对话不必伪造完整进展报告。最终标签和字段在实现规格中固定。

Go 在完整、合法输出且该轮可靠结束后创建请求，同轮同源块去重；请求存在即进入待用户阶段，不把该轮视为已完成成果待验收。解析失败保留原文，显示普通聊天答复入口，不猜选项，也不让自动交付因格式失败继续。

用户提交后，服务端把字段标题与值转换成清晰的用户答复消息，同时保存结构化关联，发送给**同一个任务的原 pi 会话／worktree**开启下一轮。若进程已结束，依已有身份校验与自动接回规则恢复；不新建第二个任务执行会话。

普通来源不依赖尚未实现的 MCP 工具或自有扩展，不宣称是挂起中的工具调用。发送答复属于用户新意图，可自动接回；仅查看问题或刷新页面不会启动模型。

### B. Agent 原生 UI 请求：独立适配

同样渲染为产品字段，但按实际 pi 版本文档核验 `confirm/select/input/editor` 等方法、取消、超时和响应格式后逐一实现能力映射，不假设协议具备多选、数字或多字段表单。

响应必须使用原请求 ID 的专用发送路径，不生成普通 RPC 命令 ID 后等待普通响应；不向聊天再补发一条会导致重复意图的 prompt。

进程退出或服务重启后，原内存等待者不保证可恢复。原生请求标为失效／待重新发起，保留记录与草稿；不把旧响应自动发给新进程，也不悄悄转成普通问题。对不支持的方法明确提示能力限制并按上游契约拒绝／取消，不伪造已支持。

### C. 系统敏感操作：复用外观，不复用授权

任务成果验收、Git 合并、交付控制可以复用字段和局部呈现，但仍执行各自可信命令、候选 SHA／预检指纹和授权校验，不能通过普通 AI 问题直接改成已完成、执行 Git 或改变权限。

普通“同意方案”只是会话内业务答案，不构成系统持久授权。AI 不得通过请求中的文案、source 或选项值伪装“可信合并审核”。后续迁移现有系统审核的位置应单独核对业务风险，不为视觉统一顺手替换现有授权流程。

## 8. 可靠性与安全

- 先持久记录答复及待派发意图，再派发给原 Agent；服务端生命周期持有发送任务，不受 WebSocket 关闭影响。
- 写入请求前可证明未发送时，允许以原操作身份重试；接受状态不明时先核查，不自动重发。对跨进程／崩溃窗口不承诺无法证明的“严格恰好一次”。
- 答复已记录但进程接回失败：保留答案并提示重试发送；核实未发送后继续，不要求用户重复填写。
- 多设备只读同步已处理状态；在编辑旧版本时收到变更，保留草稿供复制，但禁止提交过期答案。
- 普通表单禁止用于输入 API Key、密码、私钥等凭据，不提供仅视觉遮挡但会进入聊天和日志的假“安全输入”。需要凭据时引导既有服务器配置或未来独立安全凭据通道；该通道不在本轮范围。
- 沿用 Markdown 安全渲染、文本长度界限和已有登录规则；不允许表单传脚本、任意请求地址或工具参数执行器。
- 仅报告 Agent 已接受／任务真实推进的事实，不把收到交互请求、收到 HTTP／Socket 回执或成功写入管道当成开发完成。

## 9. 兼容与迁移

- 新请求成为问题状态的权威来源，`report.question` 保留兼容读取，逐步不再作为活跃交互权威。
- 历史 `report.question` 保留只读，不批量生成 pending 请求，不在升级后把旧问题全弹出来。
- 新产生但仍只有旧 question 字段的有效问题，可绑定精确当前轮次生成自由文本请求；同一来源重复报告去重。存在新结构化请求时不再从 question 重建第二份。
- 迁移使用既有 SQLite 迁移机制，保留消息、原会话身份、结果确认及 Git 数据；实施时提供备份／兼容说明。

## 10. 验收标准

### 产品与浏览器

1. 六类字段及多字段表单可提交，必填、上下限、选项与“其他”校验一致。
2. 请求只在所属聊天显示；不遮挡看板；快速切卡片、迟到事件、提交中切范围均不会串任务。
3. 收起不是拒绝或取消；重复增量不反复展开；已有草稿不丢失。
4. 桌面与手机真实浏览器检查布局、长内容滚动、输入法、键盘、焦点与可访问名称。
5. 一般聊天不冒充结构化答复；文字替代路径有明确请求关联。
6. 已回答／取消／过期／替代的历史只读；刷新恢复、双设备抢答与旧版本提交可见且正确。

### Go、存储与 Agent

7. 结构化块完整／半截／无效／超长／重复／历史兼容测试，错误不能产生伪造选项或放行交付。
8. 普通答复回到原任务 pi／worktree，恢复不另建执行会话；回答不是确认成果完成。
9. 使用隔离假 pi 验证等待、回复、拒绝、取消、进程退出和未知送达；原生路径单独验证请求 ID／运行代次，不与 prompt 混用。
10. Socket 断线、丢回执、重启、重复 operationId 和并发提交不产生重复确定副作用；不确定窗口明确阻塞，不声称已送达。
11. 阻塞型问题在服务端阻止后续自动开发／交付、完成确认与敏感操作绕过；其他任务保持独立。
12. 普通 AI 无法伪造系统来源或 Git／成果授权；跨会话请求、未知字段和密钥输入路径受控。

先开发者自测，再独立功能验收；缺少浏览器、真实模型或原生事件环境时明确标记未验证，不能用假进程结果冒充真实联调。

## 11. 建议实施顺序与边界

1. 固定产品模型、六类字段和状态，Go 持久化／幂等／Socket 命令及普通问题续接。
2. Vue 聊天内交互卡片、角标、草稿、历史和手机布局；与现有成果／自动交付门禁集成。
3. 隔离假 pi＋真实 Go 服务＋浏览器完整验证和独立验收。
4. 核验当前安装 pi 的原生交互契约，再逐项实现其确实支持的方法，不能未验证就宣布通用原生交互已接通。
5. 真实模型调用需先说明费用与测试内容；部署、Git 提交／推送另遵现有授权规则。

本提案不扩展为团队审批中心、通用工作流设计器、权限沙箱、源码编辑器、远程凭据系统或新增编排工具桥。Web 优先，PC／Android 的既有目标不改变。
